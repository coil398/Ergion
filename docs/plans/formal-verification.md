# 形式検証の実装計画

更新: 2026-09-21。状態: 計画のみ。Leanの証明、TLA+モデル、TLC検査、CIジョブはまだ作成・実行していない。

採用方針: 非同期計算の確認にはTLA+を用いることをユーザー確認済み。今回は計画までとし、ツールや依存は導入しない。

## 目的・保証の境界

Leanで数値モデルの数学的性質を証明し、TLA+／TLCで非同期実行の制御を検査する。[v0.1残作業計画](studio-oscillator.md)の数値テスト・実ブラウザ検証と組み合わせる。

| 手段 | 確認するもの | それだけでは保証しないもの |
| --- | --- | --- |
| Lean 4＋mathlib | 実数上の離散更新、明示した前提下の不変量・代数関係 | Rustの`f64`丸め、NaN不発生、コンパイラやWasm生成の正しさ |
| TLA+／TLC | 明示した環境仮定・有限モデルにおけるSafety／Liveness | 無限のキュー・実行ID全般の証明、実時間の応答上限、ブラウザ障害からの回復 |
| Rust／ブラウザテスト | 実装の解析解比較、収束、環境間一致、操作、反例の再現防止 | 入力空間全域・全スケジュールに対する形式証明 |

LeanにはFloatの論理モデルがある。ただし実数上の定理からRustの浮動小数点実装への対応は自動で得られない。初期段階は証明対象を実数モデルに限定し、丸め誤差を含むrefinementは独立した後続課題とする。[LeanのFloat仕様](https://lean-lang.org/doc/reference/latest/Basic-Types/Floating-Point-Numbers/)

## 成果物の配置・所有案

既存の`crates/`はRust、`studio/`はブラウザ、`docs/`は文書である。実装時に形式検証の専用ルート`formal/`を新設する案とし、Rust／Studioのコードへ証明ツール依存を混ぜない。現時点でこのディレクトリは存在しない。

- `formal/lean/`: Leanプロジェクト、実数モデル、定理、固定したtoolchainと依存情報。担当は数値モデルと証明のみを所有する。
- `formal/tla/`: Workerモデル、Safety／Liveness別のTLC設定。担当は非同期モデルと検査設定のみを所有する。
- `docs/verification/`: 定義・定理・actionと実コードの対応、前提、結果、未保証範囲。実装時に必要なファイルだけ作る。
- CI設定とRust／Worker回帰テスト: 統合担当が所有する。モデル担当が無断で実装の意味や受入基準を変更しない。

細かなファイル分割は各モデルの大きさが判明してから決める。導入前にLean/mathlibとTLA+ tools/TLCの公式要件、ライセンス、互換バージョンとCI実行環境を技術検証する。

## F0. 現行実装の契約と対応表を固定する

依存: 完成済みの等速直線運動および調和振動子。現在の学習単元は等速直線運動のままなので、この計画を範囲を広げるために先へ着手しない。分子動力学の実装と並行して始めない。

- [ ] 検証対象commitを固定し、Core、Lab、Worker、UI、protocolの関数・分岐と各モデル要素の対応表を作る。
- [ ] 数学的前提、Labが実行時に検証する条件、モデル上の環境仮定を別々に記録する。
- [ ] 「要求する性質」と「現実装でまだ成立していない性質」を分ける。都合の悪い分岐をモデルから削除して合格にしない。

式と理論（運動方程式、更新、テストが見るもの）は計算するRust関数の rustdoc に置き、ここでは繰り返さない。下表は実装との対応である。

| 実装 | 対応する定義・性質 |
| --- | --- |
| Coreの`rk4_step` | 4段の評価点・重み、調和振動子の一ステップ写像 |
| Coreの`velocity_verlet_step` | 半刻み速度→位置→半刻み速度の更新順序 |
| Labの設定検証・`advance`・観測値生成 | 前提条件、step上限、バッチ合成、`finished`、ゼロエネルギー分岐 |
| Workerの`load`・`start`・`pause`・`step`・`tick` | 命令処理・タイマー・Wasm状態の生成と解放 |
| UIの`load`と応答受信 | ID更新、旧ID排除、表示状態と未適用フォームの分離 |

Core自体は有限値や正の刻みを検証しない。コールバックが決定的で全出力成分を上書きすること、Verletの配列次元一致と位置依存加速度は、証明側の前提として明示する。Rustの`Fn`型だけで純粋性が証明されるとは扱わない。

完了条件: すべての初回定理・actionが実在する関数や分岐に対応し、除外した入力・環境・失敗経路を列挙できる。

## F1. 調和振動子のLean証明

依存: F0。v0.1の最初の形式検証単位。

- [ ] `m > 0`、`k > 0`、`omega² = k/m`の実数モデルと、Rustの演算順に対応するRK4／Verletの離散更新を定義する。
- [ ] RK4の一ステップが調和振動子の4次更新多項式と等しいことを証明する。これは一般ODEの大域4次収束証明とは区別する。
- [ ] Verletのゼロ状態保存と、刻みを反転した更新の可逆性を証明する。実行時の正刻み制約と、数学的に負刻みを扱う補題を区別する。
- [ ] 以下の修正二次形式がVerlet更新で不変であることを証明する。
- [ ] `abs(h * omega) < 2`の下で二次形式の正値性から状態と物理エネルギーの有界性を示す。物理エネルギー自体の厳密保存とは書かない。
- [ ] 有限回の同じ離散写像の合成について、バッチを分割しても同じ最終状態になることと、残り回数でclampしたstep上限を示す。

証明対象の候補式（未証明）:

```text
E_tilde(q, v, h) = v² / 2 + omega² * (1 - h² * omega² / 4) * q² / 2
```

完了条件: 固定環境のLeanビルドが成功し、上記定理が`by sorry`／`sorryAx`や結論そのものを仮定する独自axiomへ依存しない。`#print axioms`で依存を列挙し、標準論理上の前提と独自の仮定を記録する。[Leanのaxiom資料](https://lean-lang.org/doc/reference/latest/Axioms/)

式と演算順序の対応表をレビューし、既存Rustの解析解・収束・バッチ分割テストも通す。Lean成功だけでNative／Wasm一致を合格にしない。

## F2. 現行WorkerのTLA+／TLC検査

依存: F0。F1とは独立に進められる。モデルの数学計算はstepの更新へ抽象化し、数値計算の正しさはF1とテストへ分担する。

### 状態と遷移

- [ ] UIの実験ID、phase、未適用の変更有無、表示stepをモデル化する。
- [ ] Workerの現在ID、Wasm初期化のpending／success／failure、インスタンス有無・世代、running、タイマー予定、step・totalSteps・batchSizeをモデル化する。
- [ ] UI→WorkerとWorker→UIのFIFO列、Promiseによる命令逐次処理、生成済みだがUI未反映の応答を表現する。
- [ ] load、start、pause、step、tick、完了、初期化失敗、設定拒否、計算・シリアライズ失敗とUI受信を対応づける。
- [ ] resetは実装どおり「新しいIDのload」とする。独立したWorker命令を発明しない。

同期バッチは途中割込みがない操作として扱う一方、命令送信・Worker処理・応答生成・UI反映・次のtickを一つの原子的操作にまとめない。load中の停止→旧インスタンス解放→参照消去→新規構築→readyまたはerrorの順を保持する。

### Safety

- [ ] `0 <= step <= totalSteps`。同一実行でstepは後退せず、完了後はload以外で進まない。
- [ ] 旧IDの応答が新実験の表示を上書きしない。
- [ ] pause処理とその応答反映後は、新しいstart／step／loadなしでstepが増えない。ボタンクリック直後の停止は要求しない。
- [ ] step命令の効果は残り回数に応じて最大1。新規load後に旧timerが旧インスタンスを進めない。
- [ ] 有効インスタンスと実行タイマーはそれぞれ高々1つ。解放後のインスタンスを参照しない。
- [ ] 初期化失敗・設定拒否の状態で計算を開始しない。未適用のフォーム変更は既存Simulationを変更しない。

### Livenessと公平性

- [ ] 初期化が決着し、命令と応答が処理され続ける場合、loadがreadyまたはerrorへ到達する。
- [ ] pauseが新しいloadで置き換えられず、実行中バッチが終了する場合、停止応答または完了へ到達する。
- [ ] start後に停止・リセット・エラーがなく、tickが公平に実行される場合、有限stepで完了する。
- [ ] 継続的に実行可能な個別の命令処理・応答処理・tickに必要な弱公平性を置く。`Next`全体の公平性だけで済ませない。

タブ凍結、Worker強制終了、ブラウザクラッシュ、初期化の永久未完了は保証外と明記する。有限時間内の応答やユーザーによる再開を公平性から勝手に導かない。[公平性の解説](https://lamport.azurewebsites.net/tla/tutorial/session9.html)

### 実コード固有の例外

- loadには旧IDを拒否する分岐がない。単一UI送信元・FIFO配送・単調増加IDを前提にし、その前提を壊す入力も別モデルで検討する。
- pause待ち中でも、先に生成されたrunning応答でUI表示が一時的に戻る場合がある。「クリック直後からrunning表示へ戻らない」は現実装の保証ではない。必要なら反例を基にUX要件と修正を別途定義する。
- loadの新規構築が失敗した場合、解放済みの旧計算へは戻らない。初期化失敗後のloadで初期化を再試行する実装もない。
- 型外commandを排除する実行時検証はない。現行モデルはprotocol型を守るUIを対象とし、外部送信元を追加するならモデル・入力検証を更新する。
- 計算後のJSON変換失敗などでは、数値状態がすでに進んでいる可能性がある。「エラー時は状態不変」を仮定しない。

### 有限モデルと反例

- [ ] 初回は実験ID最大3世代、totalStepsは小さい有限集合、バッチ1〜2、命令・応答キュー長の上限を設定する。実コードで拒否するtotalSteps=0は不正入力の分岐に置く。
- [ ] IDを循環再利用して実装にない衝突を作らない。キュー上限到達でメッセージを黙って捨てない。環境の送信制限と検査範囲を明示する。
- [ ] 初期化中の連続命令、pauseとtick、resetと未反映応答、連続load、完了直前のstep、構築失敗を検査する。
- [ ] SafetyとLivenessを別設定で検査し、意図した待機・完了状態と不正なdeadlockを区別する。
- [ ] 反例は送信順・バッチ境界・応答順に読み替え、Worker／Playwrightの再現テストへ移す。初回は手動の対応づけとし、自動変換済みとは扱わない。

完了条件: 設定した全ケースの探索が完了し、指定の不変条件・時相性質を満たす。timeout・中断・状態数上限による未完了はPASSにしない。有限モデル検査を任意の世代数・キュー長についての一般証明とは呼ばない。[TLCの公式説明](https://docs.tlapl.us/using%3Atlc%3Astart)

## F3. LJとMD導入時の証明・モデル拡張

依存: MD契約の確定と全粒子対実装。F1／F2の定義・対応管理を再利用する。

- [ ] `r > 0`、`rc > 0`で標準LJのポテンシャル微分と力の関係を証明する。
- [ ] force-shifted LJについて、内側の式、カットオフのエネルギー・力の連続性、外側ゼロを証明する。衝突点を定義域から除外する。
- [ ] 最小イメージの変位定義と`rc < L/2`を明示し、ペア力の反対称性と全ペア和の合力ゼロを示す。境界の同距離分岐を無言で無視しない。
- [ ] 実数・外力なし・同時の対力更新を前提とする運動量保存と、実装の浮動小数点誤差を区別する。
- [ ] 非同期モデルへMDのモデル切替、チェックポイント読み込み、計算失敗を追加する。画面の大きい粒子配列は抽象状態とし、コピー量や性能は実測する。
- [ ] 復元後の設定・時刻・stepの整合、旧実験の応答排除、保存完了と実行状態の対応を検査する。

完了条件: 証明とモデルが実装中のLJ式・カットオフ・保存形式に一致する。数値勾配、LAMMPS比較、Native/Wasm再開のテストも通る。

## 後続の研究課題

一般ODEの存在・一意性、汎用RK4／Verletの局所・大域収束、IEEE丸め誤差を含むRustへのrefinement、全MDの長時間安定性、TLA+モデルから実装への機械的対応証明は初回の必須範囲に含めない。既存定理を確認し、個別に前提・成果・工数を見積もって進める。

mathlibにODEの基盤はあるが、汎用RK4／Verletの収束定理をそのまま使えるとはまだ確認していない。[mathlibのODE資料](https://leanprover-community.github.io/mathlib4_docs/Mathlib/Analysis/ODE/PicardLindelof.html)
